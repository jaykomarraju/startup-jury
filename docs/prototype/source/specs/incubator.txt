 ai.STARTUPJURY — Incubator Product Specification 
 Purpose of this document. This is the single source of truth for the AISJ incubator product. The prototype ships as five standalone HTML files (one per role) plus a launcher. Each file is a self-contained mock with its own hard-coded, in-memory seed data — there is no shared runtime state or backend between the files . What they do share is one domain model and one workflow, rendered through different role lenses. This spec defines that model so the build stays coherent across roles instead of five sessions each re-deriving the schema. 
 How to use it. Build against the entity model (§5), the parameter taxonomy (§6), the scoring rules (§7), and the state machines (§8) as the contract. The prototypes are the reference UI, not the schema — where a prototype's seed data disagrees with this doc, this doc wins. Read §11 (Conventions & Gotchas) before touching any prototype file.

 2. Product Overview 
 AISJ replaces manual, Excel-based jury coordination with an AI-assisted evaluation pipeline. The buyer (an incubator/accelerator) uploads founder pitch decks; the platform's AI pre-populates a suggested score (0–10) for each of the 13 standard evaluation areas using per-parameter extraction prompts. Human evaluators (Program Managers, Program Associates, Jury Members) then review and override scores, add remarks, and each contributes their own 3 role-specific parameters. Scores are aggregated and averaged across the jury to rank the pipeline. Selected startups move through a sign-up/onboarding workflow (documents → agreements → e-signature). Access is gated by plan tier and metered by evaluation credits (one credit per deck evaluated). 
 The tagline is "Venture Intelligence First."

 Entity notes 
- ParameterDefinition covers both the 13 org-level standard areas (weighted) and the role-custom parameters (3 per role, default Informational ). A parameter has: name, scope ( standard | role id), weight, description-shown-to-scorer, AI-extraction prompt.
- Evaluation is the unit of one person's scoring of one deck. Its lifecycle is pending → draft → submitted . submitted requires all applicable parameters scored.
- Assignment links a deck to an evaluator and records the role lens; it gates whether a user gets an editable vs read-only workspace.
- Deck carries an AI composite ( ai ) and a computed human composite; both are 0–10. 
 6. Parameter Taxonomy 
 6.1 Standard areas (13, weighted, org-configurable) 
 See the table in §1. Each area is scored 0–10 and has a five-band rubric (§7). Weights sum to 100% and feed the AI/human composite. Each area also has an AI extraction prompt (per-area; prototype stores these per org).

 7. Scoring & Aggregation 
 Per-area score: integer/half-step 0–10 ( step 0.5 ). AI supplies a suggested value; the human can override. 
 Band mapping ( band(v) ): v≥9 → Exceptional(0) , v≥7 → Strong(1) , v≥5 → Moderate(2) , v≥3 → Weak(3) , else Insufficient(4) . Band index also drives colour coding. 
 Rubric text per band exists per area (5 short descriptors guiding the scorer). Store as ParameterRubricBand(parameter_id, band_label, description) . 
 Composite for a deck (per evaluator): weighted average of the 13 standard-area scores by their weights. Reference implementation:
 composite = Σ(score_i × weight_i) / Σ(weight_i) ; if no weights, fall back to the raw AI value. 
 Role-custom parameters default to Informational and are excluded from the composite unless weighted ( 5% / 10% ). They are shown and averaged within their own section but reported separately, clearly labelled as custom. 
 Jury aggregation: across all jury evaluations of a deck, average the per-parameter scores (and the composite). This average is what ranks the pipeline. (Prototype uses deterministic seeded scores where real jury data isn't present.) 
 8. Workflows & State Machines 
 8.1 Evaluation lifecycle 
 pending → (scoring begins / Save draft) → draft → (Submit, all parameters scored) → submitted .
Submission is blocked until every applicable parameter has a score; on submit, the deck is marked evaluated for that evaluator and the assigned-list/stat counts update. 
 8.2 Pipeline / sign-up status 
 shortlisted , rejected , initiated , progress , completed , onboarded , archived . These label a deck's position in the buyer's funnel; initiated → progress → completed → onboarded is the sign-up happy path; archived and rejected are terminal. 
 8.3 Sign-up / onboarding workspace (three tabs) 
 Documents — required documents, each with status not_requested → awaiting → submitted → verified (with a "Verify all" bulk action). The Documents tab and the Founder tab share one document set. 
 Agreement — agreements library (e.g. Incubation Agreement, Mentorship MOU); an Authorised signatory must be assigned in-workspace (from the org's role/people list) before countersign is enabled; a signing method is chosen per record and locked once the founder signs. 
 Founder — the founder-facing view: submit documents, choose/see "How you'll sign", and sign. 
 Signing method model: provider ∈ {SignDesk, DocuSign, Adobe, Zoho, eMudhra} ; sigType ∈ {Standard e-signature, Certificate (DSC/Aadhaar/QES)} ; flags inApp , wetInk . 
 Assignment gating (PM example): a Program Manager's sign-up workspace is read-only until a Super User/Admin assigns them ( pmAssigned ); when assigned they get the full editable workspace. 
 8.4 Assignment & report stage-awareness 
 Which role parameters appear in the evaluation report depends on the stage/screen the report is opened from (detected in the prototype by which panel is visible):
- Assign stage → report shows Program associate + Program manager parameter sections.
- Intro calls stage → report shows Program associate + Program manager + Jury parameter sections (jury section as read-only "completed").
- Other stages → single-role behaviour.
In the Jury file specifically: the Assigned screen adds a Program associate reference section; Intro calls adds PA + PM reference sections; the jury's own 3 parameters are always shown (editable). 
 9. Screen / Panel Inventory 
 Panels are shown/hidden by a showPanel(name) switch (all hidden, one shown). Canonical panel ids (Super User; other roles are subsets): 
 alldecks, evaluate, upload, assign, query, myparams, coreparams, settings, introcalls, jurypipeline, forsignup, incuration, branding, curation, archive, cohortsummary, evaluatorscores, scoredrift, funnel, contactadmin, contactteam, support 
 Jury-file specifics: jassigned ( Assigned ), jurypipeline ( Evaluated ), introcalls ( My Intro calls ), repdecks / repscores / repdrift (reports). 
 My Parameters — Role configuration panel ( panel-myparams ): tabs per role ( rt-pm / rt-pa / rt-men ) with panels ( rp-pm / rp-pa / rp-men ); each parameter block has a label, weight, "Description shown during scoring", and an AI-extraction prompt. Parameters set here flow into that role's scoring view and into role-attributed reports. 
 10. Cross-Cutting Behaviours 
 My Parameters → scoring: the 3 role parameters configured in My Parameters are the exact parameters that role scores in the evaluation report; AI pre-fills a suggested score using each parameter's prompt. 
 Plans & credits: tiers standard / pro / premium . Evaluation is credit-metered — one credit per deck evaluated ; new orgs start with trial credits (e.g. 3) on Standard. Some role parameters (Pro-tier feature) require a plan to activate. 
 Permissions: parameter configuration is editable by Super Users, Program Managers and Client Admins by default; other roles are read-only unless granted "Configure 3 additional parameters" in Admin → Team & roles. 
 Support/ticketing: shared module with Admin and Super User views and a billing-approval chain. 
 Founder clarification portal: founders can respond to evaluator questions (round-trip Q&A tied to a deck). 
 11. Prototype Conventions & Gotchas (read before editing any file) 
 No cross-file state. Every file is standalone with seeded in-memory data. Nothing persists across reload; there is no shared store between roles. The launcher just base64-decodes each file into an isolated iframe. 
 Two report builders per role file — one is dead. The active report builder is the later window.openReport / jrOpen overlay (jr- classes, "Evaluate — {name}"). An earlier buildDoc (rpt- / rpt-doc, read-only document) and an ncOpen slide-over are dead code in most files. Always edit the active builder. In the Jury file, the Assigned screen opens the editable jrOpen overlay (not buildDoc ). 
 Report role sections are stage-detected via visible panel , not via call-site opts — do not rely on adding opts to onclick strings. 
 Quote hazard. Row/onclick HTML is built inside single-quoted JS strings; never inject an unescaped single-quoted literal (e.g. role:'pa' ) into them — it terminates the string. Escape ( \'pa\' ) or resolve in code. 
 Parameter names appear in multiple structures. ROLE_PARAMS (report), CUSTOM_PARAMS (jury report defaults), the My Parameters panel HTML, plus Admin → Team & roles member-config arrays and input placeholders. The Team & roles data is a separate surface and in the current prototypes still carries the old placeholder names ( Founder resilience & coachability , etc.); align it if you want full consistency. 
 Some stat cards are static. e.g. the Jury Assigned screen's "Evaluated / Drafts" counts are hard-coded and not yet wired to the live completion store ( jaDone ); the report's progress banner is live. Wire these to one store in the real build. 
 Completion tracking is illustrative. jrSubmit marks a deck done in jaDone only after all parameters are scored; seed values approximate the static stat cards. 
 Deterministic mock scores. Where real evaluator data is absent (e.g. other roles' scores shown as reference), the prototype hashes the startup name to produce stable pseudo-scores. Replace with real data. 
 Validation convention used while building: every injected change asserts anchor uniqueness, checks <div> / </div> balance, and is functionally validated in a headless DOM. Keep this discipline.
