ai.STARTUPJURY — VC Product Specification

Purpose of this document. This is the single source of truth for the AISJ VC (venture capital) product line — the sibling of the incubator spec. The prototype ships as six standalone HTML files (one per role) plus a launcher. Each file is a self-contained mock with its own hard-coded, in-memory seed data — there is no shared runtime state or backend between the files. What they do share is one domain model and one deal-flow workflow, rendered through different role lenses. This spec defines that model so the build stays coherent across roles.

Relationship to the incubator spec. The VC and incubator products run on the same engine with a role mapping and a different pipeline. Where a concept is identical (the 13 standard evaluation areas, the scoring bands, the report machinery), this doc references it rather than repeating it. What differs — the roles, the deal-flow stages, the role-specific parameters, and the onboarding surface (term sheet / diligence / fund deployment instead of incubation onboarding) — is defined here in full.

How to use it. Build against the entity model (§5), the parameter taxonomy (§6), the scoring rules (§7), and the state machines (§8) as the contract. The prototypes are the reference UI, not the schema — where a prototype's seed data disagrees with this doc, this doc wins. Read §11 (Conventions & Gotchas) before touching any prototype file.

1. Quick Reference (TL;DR)

Product. A B2B venture-intelligence SaaS for VC funds to run AI-assisted deal evaluation: source decks → AI pre-scores 13 standard areas → role-specific human scoring at each pipeline gate → committee aggregation → deal-flow progression (associate screening → partner → investment committee → term sheet → diligence → capital deployment → portfolio).

Roles (VC). Super User (Managing Partner), Partner / Principal, IC Member, Investment Associate, Analyst, Admin.

Core entities. Fund/Organization · Vehicle/Program · User(Role) · Deck(Startup/Deal) · ParameterDefinition · Evaluation · EvaluationScore/Remark · Assignment · IntroCall · PipelineStatus · TermSheet · Diligence · CapitalDeployment · Plan/Subscription · CreditLedger · SupportTicket.

Analyst is the first-line screening role: it scores incoming decks against the 13 standard areas to filter the funnel, and does not carry its own distinct 3-parameter set in the current prototype. Super User / Admin configure all parameters but do not add their own scoring set.

Scoring bands (applied per area, 0–10): 9–10 Exceptional · 7–8 Strong · 5–6 Moderate · 3–4 Weak · 0–2 Insufficient.

Key enums. - Evaluation state: pending → draft → submitted - Pipeline / deal status: sourced, screening, intro, partner_review, ic_review, aligned, term_sheet, diligence, deployed, portfolio, passed, archived - Document/diligence status: not_requested → awaiting → submitted → verified - Plan tiers: standard, pro, premium

2. Product Overview

The VC configuration of AISJ replaces spreadsheet-driven deal tracking with an AI-assisted evaluation pipeline that mirrors a fund's decision gates. A deck enters at sourcing; the platform's AI pre-populates a suggested score (0–10) for each of the 13 standard areas. The deal then moves gate by gate — Associate screening, intro calls, Partner review, Investment Committee review, alignment, term sheet, diligence — with the relevant role scoring their own 3 role-specific parameters at each stage. Scores aggregate across evaluators to rank the pipeline. Selected deals progress through term sheet, legal/investment diligence, and capital deployment into the portfolio. Access is gated by plan tier and metered by evaluation credits (one credit per deck evaluated).

The tagline is "Venture Intelligence First."

3. Role Taxonomy

VC roles (this prototype)

Role Responsibility
Super User (Managing Partner) Fund owner. Configures parameters for all roles, manages team/roles/permissions, sees all pipelines and the full stage-aware evaluation report, drives the deal from sourcing to deployment.
Partner / Principal Owns partner-stage review. Evaluates deals with the Partner parameter lens (TRL stage, PMF, Traction); hosts partner calls; advances deals toward IC.
IC Member Investment Committee evaluator. Scores deals at the IC gate with the IC lens (Barriers of entry, Scalability, Exit attractiveness); work feeds committee aggregation and the alignment call.
Investment Associate Runs the associate pipeline. Scores with the Associate lens (Thesis fit, Investment stage, Ask / Ticket size fit); manages intro calls and prepares deals for partner review.
Analyst First-line screening. Scores incoming decks against the 13 standard areas to filter the funnel before associate review.
Admin (Fund Admin) Fund administration — team & roles, required documents, agreements/term-sheet library, fund deployment capacity, billing/approvals. Shares the parameter-configuration surface with Super User.

Incubator-side mapping (parallel product line — for reference)

The same engine serves the incubator configuration via a role mapping: Super User ↔ Super User · Partner/Principal ↔ Program Manager · IC Member ↔ Jury Member · Investment Associate/Analyst ↔ Program Associate. VC replaces incubator-specific surfaces (e.g. "Seat capacity" → "Fund Deployment"; incubation onboarding → term sheet + diligence + capital deployment).

Entity notes - ParameterDefinition covers both the 13 fund-level standard areas (weighted) and the role-custom parameters (3 per scoring role, default Informational). A parameter has: name, scope (standard | role/pipeline id), weight, description-shown-to-scorer, AI-extraction prompt. - Evaluation is one person's scoring of one deck at one stage-gate. Its lifecycle is pending → draft → submitted; submitted requires all applicable parameters scored. - Assignment links a deck to an evaluator and records the role lens and the pipeline stage; it gates whether a user gets an editable vs read-only workspace at that gate. - Deck carries an AI composite and a computed human composite; both are 0–10. A deck's position is the pipeline status (§8.2). - TermSheet / Diligence / CapitalDeployment are the VC-specific onboarding chain that replaces the incubator's incubation-agreement flow.

6. Parameter Taxonomy

6.1 Standard areas (13, weighted, fund-configurable)

Identical set to the incubator product (see §1). Each area is scored 0–10, has a five-band rubric (§7), an AI-extraction prompt, and a weight defined in-file. Weights are per-fund configurable and feed the AI/human composite.

6.2 Role-specific parameters (3 per scoring role)

Default weight Informational (not weighted into the composite unless the fund raises it to 5%/10%). Each has a scorer-facing description and an AI prompt. In the prototype these are keyed by pipeline prefix in a lookup:

JP_ADDL = {
  jp: ['Thesis fit', 'Investment stage', 'Ask / Ticket size fit'],   // Investment Associate pipeline
  pp: ['TRL stage', 'Product-Market Fit', 'Traction']                // Partner pipeline
}
// IC Member set is defined alongside the report role sections:
//   ['Barriers of entry', 'Scalability', 'Exit attractiveness']  (all Informational)

Investment Associate (jp): Thesis fit — alignment with the fund's thesis, sector focus and stage. Investment stage — pre-seed/seed/post-seed classification and fit with the fund's target stage. Ask / Ticket size fit — reasonableness of the raise and fit with the fund's ticket size and reserves.

Partner / Principal (pp): TRL stage — technology maturity (TRL 1–9). Product-Market Fit — retention, repeat/organic usage, unsolicited demand. Traction — revenue, active customers, growth rate, pipeline, notable logos relative to stage.

IC Member: Barriers of entry — defensibility (IP, network effects, switching costs, data advantage, regulatory moats). Scalability — ability to grow revenue without proportional cost. Exit attractiveness — plausibility and quality of exit paths (strategic acquirers, comparable exits, timing).

Consistency rule: these role-parameter names are canonical across every file. The Super User / Admin "My Parameters — Role configuration" panel defines them for all roles; each role file's My Parameters shows the same set. Keep the standard 13 areas and these role-parameter sets identical everywhere.

7. Scoring & Aggregation

  • Per-area score: integer/half-step 0–10 (step 0.5). AI supplies a suggested value; the human can override.
  • Band mapping (band(v)): v≥9 → Exceptional(0), v≥7 → Strong(1), v≥5 → Moderate(2), v≥3 → Weak(3), else Insufficient(4). Band index also drives colour coding.
  • Composite for a deck (per evaluator): weighted average of the 13 standard-area scores by their weights: composite = Σ(score_i × weight_i) / Σ(weight_i); if no weights, fall back to the raw AI value.
  • Role-custom parameters default to Informational and are excluded from the composite unless weighted. They are shown and averaged within their own section, reported separately and clearly labelled.
  • Committee aggregation: across all evaluations of a deck at a gate, average the per-parameter scores and the composite. This average ranks the pipeline.
  • Deterministic mock scores. Where real evaluator data is absent (e.g. other roles' scores shown as reference), the prototype uses window.vcScore(name, k) — a stable hash of the startup name + parameter index producing a pseudo-score in the ~6–9 range (rounded to 0.5). This is the VC global scorer; replace with real data in the real build.

Report helpers (prototype). roAddl(rid, label, plist, note) renders a read-only additional-parameters table for a referenced role; jpAddlCell(d, i, pfx) renders an additional-parameter score chip for a pipeline prefix; JP_ADDL is the prefix→parameter-name lookup (§6.2). These mirror the incubator report machinery.

8. Workflows & State Machines

8.1 Evaluation lifecycle

pending → (scoring begins / Save draft) → draft → (Submit, all parameters scored) → submitted. Submission is blocked until every applicable parameter has a score; on submit, the deck is marked evaluated for that evaluator at that gate and the stat counts update.

8.2 Deal-flow pipeline

The VC funnel moves gate by gate:

sourced → screening (Analyst) → intro (Associate intro calls) → partner_review (Partner pipeline + partner call) → ic_review (IC pipeline) → aligned (alignment call) → term_sheet → diligence (legal + investment DD) → deployed (capital deployment) → portfolio. passed and archived are terminal.

8.3 Term sheet & diligence workspace

The VC onboarding surface (replacing the incubator's incubation-agreement flow): 1. Term Sheet — draft/issue the term sheet; an authorised signatory is assigned in-workspace before countersign; a signing method is chosen per record and locked once signed. 2. Diligence — legal DD and investment DD document sets, each item not_requested → awaiting → submitted → verified (with a "Verify all" bulk action). 3. Capital deployment — record the deployment against the fund's committed capital (the "Fund Deployment" surface that replaces the incubator's "Seat capacity").

Signing method model: provider ∈ {SignDesk, DocuSign, Adobe, Zoho, eMudhra}; sigType ∈ {Standard e-signature, Certificate (DSC/Aadhaar/QES)}; flags inApp, wetInk.

8.4 Stage-awareness & read/edit gating

Which role parameter sections appear in the evaluation report — and whether they are editable or read-only — depends on the stage/screen the report is opened from (detected in the prototype by which panel is visible). Stage flags control this:

  • pcScored — the partner-call score has been recorded → partner section shown as completed/read-only downstream.
  • partnerScored — partner-stage evaluation submitted.
  • icScored — IC score recorded.
  • icRead — IC section rendered read-only (for roles/stages that reference but cannot edit it).
  • alignCall — alignment-call stage reached → IC + upstream sections shown as read-only reference, alignment section editable.

General pattern: at each gate the current role's own parameters are editable; upstream roles' parameters are shown as read-only reference ("completed"); downstream sections are hidden until reached. This mirrors the incubator's stage-aware report, adapted to the VC gates.

9. Screen / Panel Inventory

Panels are shown/hidden by a showPanel(name) switch (all hidden, one shown). Canonical panel ids observed in the Super User file (other roles are subsets):

alldecks, upload, assign, evaluate, query, scoring, myparams, coreparams, introcalls, jurypipeline, partnerpipeline, partnercall, icpipeline, alignmentcall, decisions, diligence, investmentdd, legaldd, capital, portfolio, funnel, curation, incuration, archive, contactadmin, contactteam, support

Stage-to-panel mapping: Associate pipeline (jurypipeline / assoc), Intro calls (introcalls), Partner pipeline (partnerpipeline), Partner call (partnercall), IC pipeline (icpipeline), Alignment call (alignmentcall), IC decisions (decisions), Investment DD (investmentdd), Legal DD (legaldd), Capital deployment (capital), Portfolio (portfolio).

10. Cross-Cutting Behaviours

  • My Parameters → scoring: the 3 role parameters configured in My Parameters are the exact parameters that role scores in the evaluation report; AI pre-fills a suggested score using each parameter's prompt.
  • Plans & credits: tiers standard / pro / premium. Evaluation is credit-metered — one credit per deck evaluated; new funds start with trial credits on Standard.
  • Permissions: parameter configuration is editable by Super Users, Partners and Fund Admins by default; other roles are read-only unless granted "Configure 3 additional parameters" in Admin → Team & roles.
  • Support/ticketing: shared module with Admin and Super User views and a billing-approval chain.
  • Founder clarification portal: founders can respond to evaluator questions (round-trip Q&A tied to a deck).

11. Prototype Conventions & Gotchas (read before editing any file)

  1. Launcher uses real file links, not embedded blobs. AISJ_VC_Launcher.html opens each role via frame.src = ROLE_FILE[which] (a relative URL). All seven files (launcher + six roles + an index.html copy of the launcher) must be deployed together as one folder/site. This replaced an earlier base64-blob launcher that broke nested content (the Admin overlay) on hosted browsers — see gotcha #2. When updating a role, replace its file and redeploy the folder; no re-embedding needed.
  2. Nested Admin overlay must run same-origin. The Super User file embeds the Admin console and opens it via srcdoc (with a data:/blob fallback). This only works reliably when the role file is served as a real same-origin file over HTTP(S). Served from a blob:/data: origin (the old launcher), browsers block the nested data:/srcdoc frame with a "content is blocked" error. Keep the role files as hosted files.
  3. No cross-file state. Every file is standalone with seeded in-memory data. Nothing persists across reload; there is no shared store between roles.
  4. Two report builders per role file — one is dead. The active report builder is the later overlay; an earlier buildDoc (rpt-* document) is dead code in most files. Always edit the active builder.
  5. Report role sections are stage-detected via the visible panel, not via call-site opts. Do not rely on adding opts to onclick strings; the report reads which pipeline panel is visible and the stage flags (§8.4).
  6. Quote hazard. Row/onclick HTML is built inside single-quoted JS strings; never inject an unescaped single-quoted literal (e.g. pfx:'pp') into them — it terminates the string. Escape or resolve in code.
  7. Parameter names appear in multiple structures. JP_ADDL (report, keyed by jp/pp prefix), the IC role-section array, the My Parameters panel HTML, plus Admin → Team & roles member-config arrays. Some non-Super-User files still carry placeholder names (Program fit, Product-market fit) in their Team & roles surface — align them if you want full consistency. The Super User file is canonical.
  8. Deterministic mock scores. window.vcScore(name, k) hashes the startup name to produce stable pseudo-scores where real data is absent. Replace with real data.
  9. Validation convention used while building: every injected change asserts anchor uniqueness, checks <div>/</div> balance, and is functionally validated in a headless DOM served over HTTP (so same-origin behaviour matches production). Keep this discipline.
